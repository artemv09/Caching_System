# Caching_System

Учебный симулятор кеширования на C++20. Реализованы LRU, LFU, полная 2Q и
шаблонный `Arc_cach<Key>`. Сейчас `main.cpp` запускает фиксированный пример LIRS.

Сборка и запуск примера из корня репозитория:

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp lru_cach.cpp lfu_cach.cpp 2Q_cach.cpp -o /tmp/caching_demo
/tmp/caching_demo
```

ARC использует правила [Megiddo и Modha, Figure 4](https://www.usenix.org/legacy/events/fast03/tech/full_papers/megiddo/megiddo.pdf).
Например, `Arc_cach<int> cache(3)` или `Arc_cach<std::string> cache(3)`.
Ключ должен поддерживать копирование, `std::hash<Key>` и сравнение на равенство.
Копирование самого кеша запрещено, поскольку таблица хранит итераторы списков.

`access(key)` возвращает `true` только при наличии страницы в T1 или T2.
Обращение к B1/B2 — промах с загрузкой в T2. Новый ключ загружается в T1.
При вместимости 0 кеш остаётся пустым и всегда возвращает `false`.
`size()` учитывает только T1 и T2. В начале каждого списка находится MRU,
в конце — LRU.

Внутри `cache_one_ell_clean` сосредоточены выбор жертвы и очистка истории:
для нового ключа передаётся `None`, для возврата из истории — B1 или B2.
При возврате сначала обновляется `target_recent_size_`, затем освобождается
резидентное место, затем запрошенный узел переносится в T2.
`delete_ell_list` только переносит хвост T1/T2 в B1/B2 или удаляет хвост истории.

После завершённого запроса размеры T1 + T2, T1 + B1 и B1 + B2 не превышают
вместимость. В процессе возврата из истории B1 + B2 может временно содержать
дополнительную запись до переноса запрошенного узла в T2.

Если копирование ключа или выделение памяти при вставке не удаётся, добавленный
узел списка откатывается. Ранее вытесненная страница при этом не восстанавливается.

Проверка синтаксиса заголовка из корня репозитория:

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic -fsyntax-only -x c++ arc_cach.hpp
```

Эта команда проверяет синтаксис, но не поведение кеша и не все специализации шаблона.

Для `Lirs_cach<Key>(capacity, HIR_capacity)` приняты следующие граничные
правила реализации (это допущения проекта, а не требования задания):

- При вместимости 0 допустима только HIR-квота 0; каждый запрос — промах.
- При вместимости 1 допустимы HIR-квоты 0 и 1. Внутри используется одна
  резидентная HIR в Q без истории S: повтор последнего ключа — попадание,
  новый ключ заменяет предыдущий.
- При вместимости больше 1 требуется `0 < HIR_capacity < capacity`.
- Недопустимые квоты вызывают `std::invalid_argument` до вычитания размеров.

Целевые тесты LIRS, включая переходы, квоты и вместимость 1:

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic -D_GLIBCXX_DEBUG -I . tests/lirs_test.cpp -o /tmp/lirs_test
/tmp/lirs_test
```

Случайные проверки обычных вместимостей проверяют ограничение размера;
для вместимости 1 ответы дополнительно сверяются с моделью последнего ключа.
