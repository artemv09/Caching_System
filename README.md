# Caching_System

Учебный симулятор кеширования на C++20. Реализованы LRU, LFU, полная 2Q,
ARC и LIRS. Кеши параметризуются `Key, Value`. `main.cpp` запускает
многоуровневый кеш через `general_fun`, конфигурация читается из `config.txt`.

Сборка и запуск примера из корня репозитория:

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp creat_cach.cpp -o /tmp/caching_demo
/tmp/caching_demo
```

ARC использует правила [Megiddo и Modha, Figure 4](https://www.usenix.org/legacy/events/fast03/tech/full_papers/megiddo/megiddo.pdf).
Например, `Arc_cach<int, int> cache(3)` или `Arc_cach<std::string, int> cache(3)`.
Ключ должен поддерживать копирование, `std::hash<Key>` и сравнение на равенство.
Копирование самого кеша запрещено, поскольку таблица хранит итераторы списков.

`look_up(key)` возвращает `Access_Result<Value>` с `hit == true` только
при наличии страницы в T1 или T2. Загрузка после промаха выполняется отдельно
через `insert_value(key, value)`: B1/B2 загружаются в T2, новый ключ — в T1.
При вместимости 0 кеш остаётся пустым, `look_up` всегда возвращает промах.
`size()` учитывает только T1 и T2. В начале каждого списка находится MRU,
в конце — LRU.

Внутри `cache_one_ell_clean` сосредоточены выбор жертвы и очистка истории:
для нового ключа передаётся `None`, для возврата из истории — B1 или B2.
При возврате сначала обновляется `target_recent_size_`, затем освобождается
резидентное место, затем запрошенный узел переносится в T2.
`delete_ell_list` только переносит хвост T1/T2 в B1/B2 или удаляет хвост истории.

После завершённого запроса размеры T1 + T2, T1 + B1 и B1 + B2 не превышают
вместимость. В процессе возврата из истории B1 + B2 может временно содержать
дополнительную запись до переноса запрошенного узла в T2.

Если копирование ключа или выделение памяти при вставке не удаётся, добавленный
узел списка откатывается. Ранее вытесненная страница при этом не восстанавливается.

Проверка синтаксиса заголовка из корня репозитория:

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic -fsyntax-only -x c++ arc_cach.hpp
```

Эта команда проверяет синтаксис, но не поведение кеша и не все специализации шаблона.

Для `Lirs_cach<Key, Value>(capacity, HIR_capacity)` приняты следующие граничные
правила реализации (это допущения проекта, а не требования задания):

- При вместимости 0 допустима только HIR-квота 0; каждый запрос — промах.
- При вместимости 1 допустимы HIR-квоты 0 и 1. Внутри используется одна
  резидентная HIR в Q. Ожидается модель последнего ключа; текущий дефект
  сохранения истории при этой вместимости описан ниже.
- При вместимости больше 1 требуется `0 < HIR_capacity < capacity`.
- Недопустимые квоты вызывают `std::invalid_argument` до вычитания размеров.

Целевые тесты LIRS, включая переходы, квоты и вместимость 1:

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic -D_GLIBCXX_DEBUG -I . tests/lirs_test.cpp -o /tmp/lirs_test
/tmp/lirs_test
```

Случайные проверки обычных вместимостей проверяют ограничение размера;
для вместимости 1 ответы дополнительно сверяются с моделью последнего ключа.


## Результат вставки

Все пять политик имеют интерфейс:

```cpp
Erase_ELL<Key, Value> insert_value(const Key& key, const Value& value);
```

`Erase_ELL` объявлена в `crutch.hpp` и содержит `std::optional<Key> key_erase`
и `std::optional<Value> value_erase`. После успешного возврата оба поля пусты,
если resident-страница не вытеснялась; иначе они содержат копии ключа и значения
одной и той же жертвы. Результат владеет данными и не зависит от жизни кеша.
При вместимости 0 возвращается входная пара `{key, value}`, поскольку уровень
не может её сохранить. Это особый случай передачи страницы следующему уровню.

Вытеснение A1in -> A1out, T1 -> B1, T2 -> B2 и resident HIR -> HIR_NO_RES
возвращает данные жертвы. Удаление одной лишь ghost-записи результата не заполняет.
Повторная вставка resident-ключа не заменяет его значение и не вытесняет страницу;
ARC при этом сохраняет своё прежнее продвижение в T2. `look_up` и `erase_key`
сохраняют прежние интерфейсы. Для обычного запроса сначала вызывается `look_up`,
а после промаха — `insert_value`.

Ключ и значение жертвы копируются до её удаления. LRU/LFU сохраняют жертву
перед вставкой новой страницы; если копирование `Value` при сохранении жертвы
или создании нового `Entry` бросает исключение, содержимое остаётся прежним.
Это не обещает откат при исключении во время передачи готового результата вызывающему коду.
В LFU минимум частоты устанавливается в 1 после успешной вставки,
чтобы откат записи таблицы не оставлял неверный минимум. Для 2Q/ARC/LIRS
не заявляется восстановление ранее вытесненной страницы при последующей ошибке
загрузки. Новые копирования значения жертвы в LIRS выполняются до изменения S/Q.

В `redistribution_inc_cach` оба поля проверяются через `assert`, а для
инвалидации верхних уровней используется `key_erase`. В существующей заготовке
`redistribution_ex_cach` также обновлён тип результата `std::visit`.
Полная Exclusive-политика в рамках этого изменения не реализуется.

Проверки из корня репозитория:

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic -D_GLIBCXX_DEBUG -I. tests/two_level_combinations_test.cpp creat_cach.cpp -o two_level_tests
./two_level_tests

g++ -std=c++20 -Wall -Wextra -Wpedantic -D_GLIBCXX_DEBUG -I. tests/eviction_test.cpp creat_cach.cpp -o /tmp/eviction_test
/tmp/eviction_test
```

Первый тест проверяет все 25 комбинаций двух уровней. Второй проверяет
ключ/значение реальных жертв всех пяти политик, ghost-переходы, пустой результат,
вместимости 0/1, дубликаты, строковые ключи, значение без конструктора по умолчанию,
время жизни результата и исключения при копировании `Value` в LRU/LFU.

Расширенная проверка `/tmp/eviction_test --random` выполняет до 5000 запросов
на политику с seed 42, сверяя возвращаемые пары с независимым учётом резидентов.
Значение меняется при каждой загрузке, поэтому его нельзя восстановить только
по ключу. Отдельную политику можно выбрать, например:
`/tmp/eviction_test --random LIRS`.

## Извлечение resident-страницы

`find_del(const Key& key)` возвращает `Erase_ELL<Key, Value>` и извлекает
страницу по заданному ключу, без поиска жертвы и без обращения к `big_data`.
Для отсутствующего или non-resident ключа оба поля результата пусты, состояние
не изменяется. Для resident-ключа пара копируется до удаления данных;
после успешного извлечения `size()` уменьшается на 1. Результат владеет данными.
При вместимости 0 метод возвращает `{}` (в отличие от `insert_value`).

- LRU/LFU сохраняют пару и вызывают `erase_key`. LFU при этом использует
  существующее обновление `frequency_table` и `min_frequency`.
- 2Q переводит A1in в A1out через `move_a1in_to_a1out`, затем при превышении
  Kout вызывает `erase_a1out`. Из Am страница удаляется через `erase_key`.
- ARC переводит выбранный узел T1 в B1 или T2 в B2 через
  `move_resident_to_ghost`. Этот же помощник используется ветками T1/T2
  прежнего `delete_ell_list`, который по-прежнему выбирает хвост списка.
  `find_del` не меняет `target_recent_size_` и не вызывает REPLACE.
  Для внешнего извлечения принято правило: если B1+B2 превысило capacity,
  очищается хвост B2 через существующий `delete_ell_list(B2)`.
  T1+B1 не увеличивается; B2 в случае переполнения гарантированно непуст.
  Это ограничивает историю без вытеснения второй resident-страницы.
- LIRS проверяет наличие `node.value`, сохраняет пару и вызывает `erase_key`.
  История сохраняется или удаляется обычным `prune_S`; искусственного удержания
  ключа в S нет. Счётчики и очередь Q меняются только существующим кодом удаления.

Новая история тоже подчиняется лимитам: например, 2Q с Kout=0 сразу удаляет
созданный ghost. Очистка истории никогда не заменяет возвращаемую resident-пару.
Если копирование пары до удаления бросает исключение, страница остаётся в кеше;
откат при исключении во время передачи готового результата не обещается.

Проверка извлечения, истории, квот, удаления произвольного узла, исключений
копирования, времени жизни результата и вызовов через `std::visit`:

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic -D_GLIBCXX_DEBUG -I. tests/find_del_test.cpp creat_cach.cpp -o /tmp/find_del_test
/tmp/find_del_test
```

## Известные проблемы исходной версии

Эти проблемы отделены от изменения возвращаемого типа и не исправлены им:

- ARC: `cache_one_ell_clean` при B2-hit, пустом T1 и `p == 0` выбирает пустой
  T1. Минимальная трасса для вместимости 2: вставить 1, 2; `look_up(1)`;
  вставить 3, 2; `look_up(3)`; вставить 1. `_GLIBCXX_DEBUG` останавливается
  на `back()` пустого списка. Это также прерывает расширенный случайный тест.
  Условие непустого T1 должно охватывать обе альтернативы выбора T1.
- LIRS: при вместимости 1 история S сохраняет старые ключи. Возврат истории
  нарушает состояния LIR/HIR. Тест `tests/lirs_test.cpp`, адаптированный к
  `look_up`/`insert_value`, воспроизводит ошибку на потоке
  `1 1 2 1 3 2 1 1` с HIR=0. Новый assert обнаруживает пустое значение жертвы;
  на исходной версии тест также не проходит. Ожидаемые ответы теста сохранены.
- `parsing_cach_parametr` в `creat_cach.cpp` сравнивает массив `char name[32]`
  со строковым литералом через `name == "LIRS"`, то есть сравнивает адреса;
  нужна проверка содержимого строки. Компилятор выдаёт `-Waddress`.
- Заготовка `access_exclusive` пока не извлекает страницу из уровня попадания.
  В `redistribution_ex_cach` смешаны типы `Entry` и `Erase_ELL`; инстанцирование
  Exclusive требует дальнейшей реализации. `find_del` пока не подключена
  к многоуровневому кешу.
- Незавершённый `opt.hpp` использует необъявленные `Key_List` и
  `general_hash_table`; в сборку основного приложения он не входит.

В 2Q остаётся прежнее предупреждение `-Wswitch` для A1out в `look_up`:
ghost-промах возвращается после `switch`. Это не ошибка нового интерфейса.
