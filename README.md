# Caching System

Учебный симулятор на C++20: LRU, LFU, полная 2Q, ARC, LIRS и плоский эталон OPT/MIN.
Иерархия имеет тип `Multi_Level_Cach<Key, Value, Mode>`.

## Что где находится

| Программа | Назначение |
|---|---|
| `build-inclusive/caching_system` | Ручной запуск Inclusive |
| `build-exclusive/caching_system` | Ручной запуск Exclusive |
| `build-tests/unit_tests` | Все автоматические проверки, включая обе иерархии и `tests/my_test.cpp` |
| `build-inclusive/benchmark_test` | Полный набор паттернов и сочетаний алгоритмов в Inclusive |
| `build-exclusive/benchmark_test` | Полный набор паттернов и сочетаний алгоритмов в Exclusive |

Каждый benchmark запускает только режим своей сборки. Для сравнения Inclusive
и Exclusive запусти обе программы с одинаковыми параметрами: они создадут
одинаковые потоки запросов с seed 42.

## Сборка

Нужны G++ с поддержкой C++20 и CMake ≥3.16. Для `unit_tests` нужен GoogleTest:
CMake использует установленную библиотеку либо загружает фиксированный commit
версии 1.14. При первой загрузке нужен интернет.

Все команды выполняй из корня проекта. Три папки сборки настраиваются отдельно:

```bash
cmake -S . -B build-inclusive \
  -DCMAKE_CXX_COMPILER=g++ -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCACHE_MODE=Inclusive \
  -DBUILD_CACHE_APP=ON -DBUILD_BENCHMARK=ON -DBUILD_TESTING=OFF
cmake --build build-inclusive --parallel 2

cmake -S . -B build-exclusive \
  -DCMAKE_CXX_COMPILER=g++ -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCACHE_MODE=Exclusive \
  -DBUILD_CACHE_APP=ON -DBUILD_BENCHMARK=ON -DBUILD_TESTING=OFF
cmake --build build-exclusive --parallel 2

cmake -S . -B build-tests \
  -DCMAKE_CXX_COMPILER=g++ -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCACHE_MODE=Inclusive \
  -DBUILD_CACHE_APP=OFF -DBUILD_BENCHMARK=OFF -DBUILD_TESTING=ON
cmake --build build-tests --parallel 2
```

`-S .` указывает папку исходников, `-B` — папку результата.
`--parallel 2` разрешает до двух задач сборки одновременно. `Debug` удобен для
отладки; для измерения скорости выбирай `Release`. `compile_commands.json`
содержит команды компиляции и помогает редактору находить заголовки.

`BUILD_CACHE_APP`, `BUILD_BENCHMARK` и `BUILD_TESTING` включают соответствующие
программы из таблицы. `CACHE_MODE` выбирает режим `caching_system` и `benchmark_test`.
`unit_tests` проверяет обе иерархии при любом значении `CACHE_MODE`.

После изменения исходников повторяй `cmake --build` для нужных папок.
Команду настройки повторяй, когда меняешь параметры сборки.

## Все автоматические тесты

```bash
./build-tests/unit_tests
```

Эта команда запускает все GoogleTest-тесты: LRU, LFU, 2Q, ARC, LIRS, OPT,
Inclusive, Exclusive, ввод, генераторы и свои примеры. Тесты сравнивают результат
с ожидаемым и сообщают об ошибке при несовпадении.

Тот же полный набор можно запустить через CTest:

```bash
ctest --test-dir build-tests --output-on-failure
```

При CMake 3.16–3.19 используй `(cd build-tests && ctest --output-on-failure)`.
CTest регистрирует одну программу `unit_tests`, внутри которой запускаются все
проверки. Большой benchmark запускается отдельно.

Для отдельных групп или списка доступных проверок:

```bash
./build-tests/unit_tests --gtest_filter='Lru.*'
./build-tests/unit_tests --gtest_filter='Inclusive.*:Exclusive.*'
./build-tests/unit_tests --gtest_filter='MyCache.*'
./build-tests/unit_tests --gtest_list_tests
```

В [tests/my_test.cpp](tests/my_test.cpp) добавляй свои `TEST(Group, Name)` ниже
примера. Файл уже включён в `unit_tests`. После изменения достаточно:

```bash
cmake --build build-tests --target unit_tests --parallel 2
./build-tests/unit_tests
```

`EXPECT_EQ(a, b)` проверяет равенство, `ASSERT_NE(pointer, nullptr)` останавливает
тест при нулевом указателе. `SCOPED_TRACE` добавляет пояснение к сообщению об ошибке.

## Ручной запуск кеша

В [config.txt](config.txt) находятся число уровней и их алгоритмы:

```text
2
LRU
LFU
```

Имена: `LRU`, `LFU`, `2Q`, `ARC`, `LIRS`. Регистр значим.
Запускай из корня проекта: программа ищет `config.txt` в текущей папке.

```bash
./build-inclusive/caching_system
# либо:
./build-exclusive/caching_system
```

Затем вводи вместимости уровней, число запросов N и N ключей. Например, для
конфигурации выше:

```text
2 4
8
1 2 1 3 4 1 2 4
```

Здесь L1 вмещает 2 страницы, L2 — 4 страницы; дальше идут 8 запросов.
Если уровень использует LIRS, сразу после его вместимости вводится HIR.
Например, для файла `2 LRU LIRS` начало ввода будет `2 4 1`: L1=2, L2=4, HIR=1.

Ключи ручного примера — от 1 до 10; значение равно `100 * key`.
Программа печатает найденные значения, попадания по уровням и результат OPT.
После N ключей ждать EOF или нажимать Ctrl+D не требуется.

Число уровней — 1..64, N — 0..1 000 000, вместимости — 0..1 000 000.
Inclusive требует положительной вместимости всех уровней; Exclusive допускает нулевые.

## Полные прогоны с паттернами

```bash
./build-inclusive/benchmark_test
# либо:
./build-exclusive/benchmark_test
```

Первая строка вывода показывает режим: `Mode: Inclusive` или `Mode: Exclusive`.
Названия паттернов в терминале выделяются красным; при сохранении вывода в файл остаётся обычный текст.

Затем программа запрашивает по порядку:

1. L — количество уровней.
2. K — количество выбранных алгоритмов.
3. N — количество запросов в каждом паттерне.
4. K разных имён алгоритмов.
5. Вместимости уровней от L1 до LL. Если среди алгоритмов есть LIRS, после
   каждой вместимости вводится HIR для этого уровня.

Например, два уровня, два алгоритма, 100 запросов на паттерн:

```text
2 2 100
LRU LFU
2 4
```

Для каждого паттерна программа проверит четыре сочетания: LRU/LRU, LFU/LRU,
LRU/LFU и LFU/LFU. Все они проходят только в режиме запущенной программы.
Каждая пара «паттерн + конфигурация» начинает с пустой иерархии.

Пример со всеми пятью алгоритмами и LIRS-параметрами:

```text
2 5 100
LRU LFU 2Q ARC LIRS
2 1
4 1
```

Здесь будет 25 сочетаний на каждый паттерн. Всего допускается не более
10 000 сочетаний K^L. В Inclusive вместимости должны быть положительными,
в Exclusive допускаются нулевые. N=0 допустимо и даёт нулевые попадания.

Запросы генерируются автоматически, ключи находятся в диапазоне 1..1 000 000.
Случайные паттерны используют seed 42 — начальное состояние генератора, поэтому
повторный запуск с теми же параметрами и той же стандартной библиотекой воспроизводится.
Есть и неслучайные нагрузки: циклы, повтор одного ключа, сканирование, серии повторов,
горячая группа, смена популярности. Генераторы находятся в
[tests/request_patterns.hpp](tests/request_patterns.hpp).

Вывод содержит попадания по уровням, сумму попаданий, промахи, процент попаданий
и плоский OPT: его вместимость равна последнему уровню для Inclusive и сумме
уровней для Exclusive. Это ориентир для сравнения попаданий; он не доказывает
глобальную оптимальность иерархии. Benchmark выводит статистику экспериментов;
проверки с ожидаемыми ответами запускаются через `unit_tests`.

Для сравнения двух режимов на одинаковых параметрах и сохранения результатов:

```bash
printf '2 2 100\nLRU LFU\n2 4\n' | ./build-inclusive/benchmark_test > benchmark-inclusive.txt
printf '2 2 100\nLRU LFU\n2 4\n' | ./build-exclusive/benchmark_test > benchmark-exclusive.txt
```

`printf` передаёт ответы программе, а `>` записывает её вывод в файл.
Параметры передаются через обычный ввод; CSV и параметры вроде `--count` здесь не используются.

`make_patterns` выбирает размеры групп по вместимостям. Рабочие размеры групп
ограничены диапазоном 2..62500, чтобы W−1 и 16×W оставались допустимыми.
Сами вместимости кешей не меняются. За этим диапазоном нагрузки уже не соответствуют
точным границам C−1/C+1. Среди случайных потоков сохранён `uniform_w10000` —
равномерные запросы к ключам 1..10000.

## Дополнительная диагностика

При настройке отдельной тестовой сборки можно добавить `-DCACHE_SANITIZERS=ON`
для ASan/UBSan: они ищут ошибки памяти и неопределённое поведение при запуске.
`-DCACHE_DEBUG_ITERATORS=ON` включает проверки итераторов libstdc++.
GoogleTest собирается с теми же флагами. Уже распакованный GoogleTest можно указать
через `-DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=/путь/к/googletest`.

## Контракты и объяснения

`look_up` возвращает указатель на резидентное значение и обновляет политику доступа.
Ghost означает промах. Указатель нельзя использовать после удаления или вытеснения записи.
`insert_value` загружает отсутствующую страницу и возвращает вытесненную пару, если она есть.
Дубликат сохраняет прежнее значение и приоритет. При capacity=0 вставляемая пара возвращается обратно.

LRU использует начало списка как MRU; LFU начинает частоту с 1 и разрешает равенства по LRU.
В полной 2Q A1in — FIFO, Am — LRU; Kin — порог выбора жертвы, не квота при прогреве.
В ARC p — целевой размер T1. В LIRS S — история, Q — резидентные HIR.
LIRS допускает (capacity,HIR)=(0,0), (1,0), (1,1); при capacity>1 нужно 1≤HIR<capacity.
После внешнего удаления освободившаяся LIR-квота заполняется при загрузке или HIR-hit.

`erase_key` возвращает true только для резидента; существующую ghost-запись не удаляет.
`extract_entry` возвращает самостоятельную копию key/value и удаляет резидента.

| Политика | История после erase / extract |
|---|---|
| LRU, LFU | Истории нет |
| 2Q | erase стирает резидента; extract из A1in создаёт A1out, из Am истории не создаёт |
| ARC | erase стирает резидента; extract переводит T1→B1 либо T2→B2 |
| LIRS | Обе операции сохраняют нерезидентную запись, если она остаётся в S после pruning |

Inclusive сохраняет включение резидентов верхнего уровня в нижние и инвалидирует верхние
копии при нижнем вытеснении. Exclusive хранит резидентную страницу ровно на одном уровне,
поднимает нижний hit в L1 и передаёт жертв вниз. Один запрос даёт максимум один hit.

`snapshot() const` возвращает копию резидентов, очередей и параметров; не обновляет приоритеты.
Поле `consistent` помогает тестам проверять внутренние связи. Это диагностика, не операция горячего пути.
После исключения вставки прежнее содержимое не обещается: LIRS очищается до рабочего пустого
состояния, 2Q/ARC ограничивают историю после уже выполненного вытеснения.
Исторические отчёты находятся в архиве документации.

Прежние подробные объяснения и отчёты сохранены в [docs/archive](docs/archive/README.md).
Они описывают старую версию; актуальные команды запуска приведены выше.
